# Building blocks

Implement one player-visible checkpoint at a time. Deliver its playable build and checks, then wait for
player feedback before the next phase. Feedback may split or reorder work. File-level tasks need no separate pause.
[CONTRACT.md](CONTRACT.md) owns implemented behavior; the current checkpoint is [Phase 3](PHASE3_PLAYCHECK.md).

## Direction

A painted fantasy hub connects friends to dungeons and race groups to isolated copies of the same challenge.
Parties support one to five, including solo; premade friends stay together. Future queues keep a chosen class
or assign class/group with an optional role hint. Classes and themes need player approval.
One immutable race specification fixes layout, encounters, keys, modifiers and loot opportunities;
each party owns separate progress. Visible doorways do not prescribe hosting processes.

Reuse KayKit assets, TD01's movement/camera and focused lessons. Dungeon rules own simulation;
no tower, mining, crafting, research or era systems are inherited. No talent tree is planned.
Use the [asset plan](KAYKIT_ASSET_PLAN.md) for measured pieces, lighting, multilevel decisions and phase checkpoints.
Use the [balance plan](BALANCE_PLAN.md) for deterministic composition/seed experiments and human acceptance.

## Sequence and acceptance

| Block                           | Outcome and required checks                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 01 · Hub — implemented          | Isolated entry, credited assets, one visual preset/player, central marker, distinct friends/race mouths, honest prompts. Camera-relative equal-speed movement, boundary/monument collision, focus release, resizing and real Chrome checks. Player judges theme, movement and readability.                                                                                                                                    |
| 02 · Enter/return — implemented | Deliberate proximity-checked Friends action reaches a fixed room and returns to the original arrival. Transfers lock/reject repeats and clear input. Check both directions, interrupted input, scale and transition feel.                                                                                                                                                                                                     |
| 03A · Section library           | Shared floor/grid/passage dimensions; straight, corner, T, crossroads, small/large rooms and deliberate dead ends. Own sockets, orientations and collision; keep props out of clearances. Check rotated joins, five-body clearance and camera occlusion. Authored Phase 2 arrangements are implemented; group play remains unverified.                                                                                        |
| 03B · Seeded route              | Connect approved sections from a visible seed; reject overlaps and mismatched joins, seal unused sockets, ensure entrance/exit reachability and safe spawns. Walls must preserve character visibility. Finish/return, replay identical seeds and compare a seed corpus. Phase 3 implements a bounded two-floor generator, native stair traversal, four play cameras and side inspection. Expanded generation remains planned. |
| 04 · Enemy                      | One skeleton with bounded detection/navigation, health/death, telegraphed attack, cooldown and simulation-owned damage. Show player health, defeat/return and fresh-attempt reset. Test approach, evade, loss and restart.                                                                                                                                                                                                    |
| 05 · Combat                     | One weapon with validated reach/target/cooldown and no attacks through walls. Show anticipation/impact/recovery; death occurs once and releases targeting/collision. Add a route encounter; test win/loss/repeated input.                                                                                                                                                                                                     |
| 05A · Classes                   | Approve a small catalog with one weapon/distinct mechanic each, viable solo without required healer/tank. Select before entry, freeze per run and test every class.                                                                                                                                                                                                                                                           |
| 05B · Scaling                   | Drive actual commands in deterministic simulations across every supported size/composition, including duplicates and missing roles. Agree survival/time targets, compare bounded candidates, report worst cases/deaths/stalls, use held-out seeds and reject impossible solo fights. Record machine/commands/limits; player-check solo/five and repeat after combat changes.                                                  |
| 06 · Key/lock                   | Reachable visible key, proximity collection, authoritative ownership/unlock and explained rejection. Show required/held keys; decide consumption. Never generate a key behind its own lock. Player must understand and finish unaided.                                                                                                                                                                                        |
| 07 · Timer/results              | Define exact simulation start/finish, exclude hub time, distinguish complete/fail/abandon, and offer same-challenge retry/return. Specify practice pause/focus behavior; test interrupted frames/retries.                                                                                                                                                                                                                     |
| 08 · Run setup                  | Explicit or once-resolved random approved theme, frozen in the race specification. Validate keys/timing combinations, preview rules, reject mid-run changes and impossible disabled-key locks. Balance-check themes; test every combination.                                                                                                                                                                                  |
| 09 · Loot/suffix                | One wearable/stat and small named suffix pool. Seed opportunities separately from party collection; award once, explain effect, validate one-slot equip/unequip and define loss/retention. Add pool setup choice; test duplicate collection/rolls/stats.                                                                                                                                                                      |
| 10 · Upgrade                    | One currency/award event and hub purchase with visible balance/cost/effect. Reject unaffordable/duplicate tiers; carry effects into friends runs and define equal competitive power. Test payment and combat.                                                                                                                                                                                                                 |
| 11 · Skill                      | One active skill with explicit unlock, target/range/cooldown validation and readable feedback. Handle locked/ready/cooldown, death, transfer and restart. Player judges whether it earns its control.                                                                                                                                                                                                                         |
| 12 · Shared hub                 | Reuse the platform session contract. Version commands/snapshots, host state, assign safe unique identities and validate input/rates at ingress and rules. Two actual browsers must agree on movement/membership; disconnect releases slots.                                                                                                                                                                                   |
| 13 · Friends party              | Deliberate join/leave, size 1–5 with sixth rejected, premades intact, chosen/assigned-class queues and optional role hint. Show assignment/leader/readiness, freeze starting roster/scaling, avoid disconnect exploits and restrict rules to leader. Define defeat/revival/rejoin; check all sizes/modes, full/delta state and real-browser completion.                                                                       |
| 14 · Isolated copies            | One immutable challenge, separate party progress/tunnel ownership. Reject cross-instance actions; keep geometry/opportunities equal and damage/keys/loot/time separate. Reuse visible doors as needed; dispose abandoned/completed instances. Verify with multiple clients.                                                                                                                                                   |
| 15 · Race start                 | Approve group count and size brackets, consistent theme/difficulty/scaling, locked roster/seed/suffixes/rules/loadout. Wait for all clients, countdown and start at one host tick. Time survives focus/network delay; reject late changes and define disconnect/timeout/abandonment.                                                                                                                                          |
| 16 · Race finish                | Host records immutable finish ticks once; remaining parties continue. Show active/failed/finished status, define ties/order, compare results, return safely and explicitly rematch with a fresh specification. Test duplicate finishes/disconnects.                                                                                                                                                                           |
| 17 · Recovery                   | Agree retained progress; version saves for items/upgrades/skills separately from competitive rules. Validate bounds, corrupt/unsupported recovery, missing fields/migrations, full/delta snapshots and deterministic continuation. Player checks close/reopen promises.                                                                                                                                                       |
| 18 · Polish                     | Address recorded feedback and confusing prompts before expansion. Test five real players, target viewport/devices and measured hardware. Audio needs gesture/ownership/credits. Complete friends/race acceptance and record implemented limits before proposing content.                                                                                                                                                      |
